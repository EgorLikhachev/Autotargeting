# Заметки по разработке: кольцевой буфер кадров в разделяемой памяти (TG26-160)

**Дата:** 2026-08-17 · **Крейт:** `crates/shmem-buffer` · **Решение:** ADR D-013

## 1. Что реализовано

SPMC-кольцо (single producer, multi consumer) для видеокадров в разделяемой
памяти: продюсер публикует NV12/RGB24-кадры, неограниченное число
независимых потребителей (потоки и процессы) читают те же кадры zero-copy;
`FrameGuard` (RAII) гарантирует, что занятый слот не перезаписывается;
заполненный буфер — drop-new (Вариант A): продюсер никогда не блокируется.

- `layout.rs` — `#[repr(C)]` POD-контракты (64Б header/slot, пиннинг офсетов тестами)
- `shm.rs` — memfd + linkat(/dev/shm) + mmap (Linux; attach по имени)
- `ring.rs` — CAS-протокол, FrameGuard, ример протухших слотов
- examples: `shmem_producer`, `shmem_consumer` (torn-read детектор), `shmem_reaper`
- тесты: 15 unit + 7 acceptance (кросс-платформенно) + 2 linux-мультипроцессных
  (`--include-ignored`) + criterion-бенч

## 2. Протокол одним абзацем

Единственное слово синхронизации на слот — `ref_count: AtomicU32`:
`0` = готов/без читателей, `1..MAX-1` = готов/N читателей, `u32::MAX` =
WRITER_LOCK. Продюсер: `CAS(0→MAX)` → memcpy данных → метаданные →
`frame_id.store(Release)` → **`ref_count.store(0, Release)`** →
`write_seq.store(Release)`. Читатель: load `write_seq` (Acquire) → CAS-цепочка
`0→1` или `n→n+1` → валидация `frame_id` (seqlock-страховка от оборота
кольца) → чтение → `Drop` декрементирует. Запись и чтение одного слота
взаимоисключены по построению: обе стороны соревнуют одним CAS на одном слове.

## 3. Бюджет памяти (проверен тестом `acceptance_segment_memory_budget`)

| Режим | Кадр | Сегмент ×10 (NV12 / RGB24) |
|---|---|---|
| 320×240 NV12 | 115 КБ | 1.1 МБ / — |
| 640×480 | 460 КБ / 921 КБ | **4.4 МБ** / 8.8 МБ |
| 1280×720 | 1.38 МБ / 2.76 МБ | 13.2 МБ / 26.4 МБ |

Дефолт (10 × 640×480 NV12) = 4.4 МБ ≈ 0.12% RAM Orange Pi 5 (3.8 ГБ).

## 4. Ограничения реализации

1. **SPMC.** Мульти-продюсер не поддерживается (камера одна). Протокол
   полагается на единственного писателя `write_seq`.
2. **Оповещение — polling.** `next_after`/`latest` + `yield_now`. При
   60–187 FPS (кадр каждые 5–16 мс) поллинг адекватен; futex на SHM —
   резервная оптимизация (P2), API не блокирует её добавление.
3. **Крэш потребителя** → `ref_count` «зависает» → слот выпадает из ротации.
   Продюсер продолжает работать (свойство drop-new), ёмкость деградирует.
   Лечение — `shmem_reaper` / `recover_stale_slots` (мёртвый pid по
   `kill(pid,0)` + возраст кадра, двойная проверка). Остаточный риск:
   читатель взял слот, но ещё не записал `holder_pid` — ример требует
   «кадр старше max_age», чтобы не срезать живых.
4. **Lock-free атомики — предположение платформ.** Формально межпроцессные
   атомики вне Rust memory-модель; на всех целях проекта (x86_64,
   aarch64) 32/64-битные атомики lock-free аппаратно. Рантайм-проверка
   `is_lock_free()` опущена (недоступна в части окружений сборки).
5. **Linux-only для межпроцессного режима** (memfd/linkat/mmap).
   Внутрипроцессная арена (`create_in_process`) — любая ОС: протокол и
   тесты идентичны, SHM-специфика изолирована в `shm.rs`.
6. **Именование сегментов**: `linkat(AT_EMPTY_PATH)` memfd →
   `/dev/shm/<name>` (для memfd капабилитет не нужен). Уничтожение
   продюсера оставляет линк — застрявший сегмент убирает
   `remove_segment()`/rm. Проверка «сегмент существует» → `SegmentExists`.
7. **`panic=abort` в release**: паника потребителя убивает процесс целиком
   (guard не успевает дропнуться) — это и есть сценарий римера. В dev
   (unwind) guard дропается корректно (тест `guard_survives_panic`).

## 5. Отчёт: почему разработка останавливалась (пост-мортем, 2026-08-17)

Разработка TG26-160 пережила ~40 минут тупика. Полная цепочка причин:

### 5.1 Корневые дефекты (найдены и исправлены)

| # | Дефект | Следствие |
|---|---|---|
| 1 | **Пропущен отпуск слота**: в `publish()` после записи кадра не было `ref_count.store(0, Release)` — слот навсегда оставался в WRITER_LOCK | Каждый опубликованный слот «умирал»; читатели бесконечно ждали кадры → **зависание тест-бинарника** (стресс-тест) |
| 2 | **`alloc::alloc` без обнуления** в арене: `SlotMeta` получал мусорные `ref_count`/`frame_id` из повторно используемой кучи | Order-dependent каскад: тесты поодиночке зелёные, в suites падают все после освобождения памяти стресс-тестом (свежие страницы ОС = нули → первый прогон «везучий») |
| 3 | **Дизайн тестов**: стресс ждал магическое число кадров (drop-new законно уменьшает финальный id); walk-тест не учёл окно `capacity`; acceptance держал не тот слот (latest вместо старейшего — цели следующей записи) | Ложные фейлы/вечные ожидания, маскировавшие баги 1–2 |

### 5.2 Усилители окружения (почему поиск занял так долго)

- **OneDrive-каталог сборки**: линковка тест-бинарника в синхронизируемом
  `target/` — минуты вместо секунд, файловые блокировки; вывод прогонов
  скрывался буферизацией пайпов (`grep|head`), до последнего не видно было
  даже `running N tests`.
- **Осиротевшие процессы**: `TaskStop` убивал ssh/оболочку, но не дочерние
  cargo/test-бинарники — они держали блокировки и портили следующую
  диагностику (нашёлся висящий `shmem_buffer-*.exe` в tasklist).
- **Отсутствие дедлайнов в тестах**: баг протокола обязан падать паникой
  за секунды, а не подвешивать набор навсегда.

### 5.3 Введённые практики (чтобы не повторялось)

1. **Жёсткие дедлайны** во всех потенциально-циклических тестах
   (`stress` — 60 с panic; читатели — выход по «тихому» стриму).
2. **Bounded-прогоны**: каждый тест/сборка под внешним `timeout`.
3. **Сборка вне OneDrive**: `CARGO_TARGET_DIR=$LOCALAPPDATA/...` (для
   Windows+OneDrive окружений). В CI (Linux) не требуется.
4. **Чистка сирот** перед диагностикой: `taskkill cargo/rustc/test-exe`.
5. **Нулевая толерантность к «зависло»**: любой зависший тест = баг
   дизайна теста, даже если код формально корректен.

### 5.4 Микро-оптимизации (по требованию ревью)

- `frame_size`: `px*3/2` → `(px*3) >> 1` (деление → сдвиг; компилятор
  сворачивал и раньше, теперь зафиксировано явно).
- `next_after`: `capacity` поднимается из header **один раз** на вызов
  (было до 3 загрузок за итерацию retry-цикла).
- Горячий путь публикации — memcpy-доминирован (460 КБ ≈ десятки мкс);
  атомарные операции (~нс) не влияют на профиль — `% capacity`
  (u64-деление) оставлен как есть: замена на u32-деление меняет
  корректность при id ≥ 2³², выигрыш < 0.01% от memcpy.

## 6. Как проверить (приёмка)

```bash
# Кросс-платформенно (x86-dev):
cargo test -p shmem-buffer            # 15 unit + 7 acceptance + 2 doctest
cargo bench -p shmem-buffer           # publish / acquire / roundtrip
cargo clippy -p shmem-buffer --all-targets -- -D warnings

# Linux / Orange Pi 5 (мультипроцесс):
cargo build --release -p shmem-buffer --examples
cargo test -p shmem-buffer --test acceptance -- --include-ignored

# Вручную (два терминала):
./target/release/examples/shmem_producer --name demo.frames --fps 30 --seconds 10
./target/release/examples/shmem_consumer --name demo.frames --mode next
./target/release/examples/shmem_consumer --name demo.frames --mode slow --hold-ms 300
```

## 7. Выход на смежные задачи (вне скоупа TG26-160)

- **rknn-bridge zero-copy** (SDD §15 #2): memfd можно передать в bridge
  через SCM_RIGHTS — мост уже спроектирован под это (`shm_fd` в протоколе).
- **Интеграция в runtime** (`run_full()`): продюсер = конвейер
  video-capture→convert→publish; потребители — cv-inference/tracker/recorder.
- C++ FFI: layout `#[repr(C)]` + два CAS — C++-клиент тривиален; cbindgen
  по требованию.
