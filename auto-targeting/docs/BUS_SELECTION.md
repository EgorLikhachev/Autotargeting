# Выбор шины событий/данных между компонентами (исследование)

**Дата:** 2026-08-18 · **Статус:** ✅ выполнено — Zenoh принят (D-014,
прототип x86+RK3588); детектор уже на шине (D-015). Миграция остальных
компонентов — [BUS_MIGRATION_PLAN.md](BUS_MIGRATION_PLAN.md).
**Контекст:** система делится на компоненты (видео, CV, телеметрия АП,
запись видео, сопровождение, конфигурация) — нужен единый механизм передачи
**событий и лёгких данных** между ними. Видеокадры уже живут в SHM-кольце
(`shmem-buffer`, D-013) и через шину **не** передаются.

---

## 1. Требования к шине (из архитектуры проекта)

| # | Требование | Обоснование |
|---|---|---|
| R1 | Pub/Sub 1:N и N:M между **процессами** на одном хосте (RK3588) | детекции → трекер+рекордер+GCS-мост; телеметрия → все |
| R2 | Payloads: детекции (~1–10 КБ), телеметрия АП (десятки байт @10–50 Гц), команды/конфиг (<1 КБ) | кадры — вне шины (SHM-кольцо) |
| R3 | Латентность IPC ≤ 1 мс (цель), ≤ 5 мс (допуск) | петля детекция→команда; watchdog-бюджеты (command 10 Гц) |
| R4 | Без брокера-демона либо встраиваемый брокер | каждый демон на БВС = точка отказа (стенд и так нестабилен) |
| R5 | Rust-first API, tokio-совместимость | весь workspace на Rust/async |
| R6 | Платформы: Linux aarch64 (цель), x86_64 (dev/CI); Windows-dev — желательно | текущая среда разработки |
| R7 | Минимальные зависимости, vendoring, офлайн-сборка | deployment на борт |
| R8 | Лицензия, совместимая с MIT/Apache-2.0 | лицензия проекта |
| R9 | Умеренная сложность: фиксированный набор компонентов (~6), discovery необязателен | нам не нужен облачный сервис-меш |
| R10 | Масштабируемость на второй хост (компаньон↔наземка) — nice-to-have | основной канал с GCS — MAVLink, отдельный |

## 3. Плюсы и минусы по вариантам

### 3.1 ROS 2 + rclrs
**Плюсы:** стандарт робототехники; rviz2/rosbag2/ros2-cli инструментарий;
QoS, discovery, actions/params из коробки; rclrs признан официальным
(FOSDEM 2026); гигантская экосистема драйверов.
**Минусы:** DDS-ядро = тяжёлые зависимости и капризный тюнинг (FOC-профили,
 multicast); rclrs **не входит в дистрибутив** — colcon-оверлей, то есть
сборка-из-исходников поверх ROS на борту; сотни МБ образа; латентность и
footprint для 6 компонентов избыточны; наш GCS-канал — MAVLink, ROS-типы не
нужны. **Явный оверкилл по всем требованиям R2–R7.**

### 3.2 Zenoh
**Плюсы:** чистый Rust, один primary-крейт; **брокер не нужен** (peer-to-peer,
unix-сокет/SHM-транспорт на хосте); pub/sub + query (для конфига/запросов
«последнее значение»); латентность единицы–десятки мкс; dual-лицензия
Apache-2.0 доступна; движется очень активно; проверен роботикой (официальный
rmw_zenoh, PX4-мосты); хорошо документирован; Windows поддерживается.
**Плюсы (для C++-компонентов):** официальные биндинги — zenoh-c (C API,
свежие релизы 1.8/1.9.0, март–апрель 2026) и zenoh-cpp (header-only,
поверх zenoh-c и zenoh-pico; с 1.0 API зеркалит Rust-версию; есть
Yocto/OE-рецепты); rknn-bridge сможет говорить на шине напрямую.
**Минусы:** young-ish API (1.x стабилен, но экосистема младше ROS); zenoh-cpp заявлен «under active development» (возможны ломки minor-версий);
крейт-дерево немаленькое (~50 транзитивных) — vendoring-лок больше;
продвинутые фичи (storage/queryables) нам не нужны — берём pub/sub+query.

### 3.3 iceoryx2
**Плюсы:** zero-copy lock-free SHM pub/sub, латентность до единиц мкс; чистый
Rust, без сети-стека; идеально ложится на «один хост» (R1); Apache-2.0;
статус Eclipse, активная разработка; C/C++ API — если детектор уйдёт в C++.
**Минусы:** **без TCP** (второй хост — только своим мостом); pre-1.0 API
(0.9.x) — возможны ломки; сервис-модель требует файла/SHM-ресурсов per-topic
(чистка после крэшей — наш опыт с /dev/shm актуален); меньше готовых
интеграций, чем у ZeroMQ/Zenoh.

### 3.4 ZeroMQ (libzmq+zmq2 | zeromq.rs)
**Плюсы (libzmq):** эталонная библиотека, предсказуемая семантика; паттерны
PUB/SUB+PUSH/PULL закрывают R1; IPC-транспорт десятки мкс; MPL совместима с
дистрибуцией.
**Минусы (libzmq):** C-зависимость (cc+libzmq в образ, кросс-сборка);
**нет discovery/автопереподключения топиков** (узлы знают адреса — ок для
нас); PUB/SUB теряет сообщения при медленном подписчике (нужен XPUB-обвяз);
sync-API — обёртки под tokio вручную.
**Минусы (zeromq.rs):** развитие медленное, паттерны неполные — риск.

### 3.5 NNG
**Плюсы:** зрелый наследник nanomsg; паттерн BUS — редкая полезность;
C-ядро стабильно; MIT.
**Минусы:** те же C-зависимости; Rust-обёртки второго эшелона
(`nng` синхронный, async-вариант мёртв); сообщество меньше ZeroMQ; для нас
ничего сверх ZeroMQ.

### 3.6 NATS
**Плюсы:** простая модель subject'ов; queue-groups; отличный `async-nats`;
 JetStream если вдруг нужна история.
**Минусы:** **брокер-демон ~20 МБ (Go)** на борту — против R4; центральная
точка отказа; TCP-only (нет unix-сокета) — лишний стек для локального IPC;
облачная родословная.

### 3.7 MQTT (rumqttc)
**Плюсы:** минимум概念; QoS-уровни; LWT для «компонент умер» — красиво для
телеметрии; rumqtld — крошечный Rust-брокер.
**Минусы:** модель топиков плоская, request/reply — костыли; QoS1 добавляет
латентность; брокер всё же нужен (R4); для command-трафика семантика
слабее.

### 3.8 Кастом UDS+serde (базлайн)
**Плюсы:** ноль зависимостей; полный контроль семантики (reliable commands /
best-effort telemetry); паттерн уже обкатан в rknn-bridge (endianness, JSON);
проще некуда для 6 фиксированных компонентов (R9).
**Минусы:** всё своими руками: маршрутизация 1:N (fan-out), переподключение,
версионирование схем, мониторинг; нет готовых инструментов (топологию не
посмотреть); второй хост — свой протокол поверх TCP; растёт — превращается
в собственный ZeroMQ.

## 5. Рекомендация (шорт-лист для прототипа)

Прототипировать на x86 + RK3588 **двух финалистов** + базлайн-замер кастома:

1. **Zenoh (peer-to-peer, IPC/unix-transport)** — основной кандидат:
   закрывает R1–R8 + R10, Rust-native, без демона; pub/sub для детекций/
   телеметрии + query для конфигурации.
2. **iceoryx2** — кандидат №2: минимально возможная латентность и футпринт
   (zero-copy, pure Rust, no-network); проверить стабильность pre-1.0 API и
   поведение при крэшах потребителей (наш опыт с SHM-чистками!).
3. **Кастом UDS** — как контрольная точка по латентности (у нас уже есть
   паттерн), не как целевое решение.

**Отклонены:** ROS 2 (R2–R7: вес/зависимости/оверлей-сборка rclrs при
отсутствии ROS-экосистемы в проекте), NATS/MQTT (брокер-демон, R4), NNG
(ничего сверх ZMQ, слабее Rust-обвязка), zeromq.rs (динамика развития).

**Открытые вопросы к прототипу:** латентность pub/sub на A55 под нагрузкой
(NPU-инференс параллельно); поведение при kill -9 подписчика/издателя;
размер vendored-зависимостей; удобство сериализации (serde_json vs CBOR vs
bincode) на 1–10 КБ payload.
