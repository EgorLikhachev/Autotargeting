# Перф-аудит и оптимизация 2026-08 (полный проход)

**Дата:** 2026-08-18 · **Устройство:** Orange Pi 5 (RK3588, 8× Cortex-A55 @1.8 ГГц)
**Метод:** criterion-бенчи, A/B на одном железе (baseline → оптимизация),
одинаковые релизные флаги (`opt3, thin LTO, codegen-units=1`).
**Тесты:** все затронутые крейты зелёные на x86 и aarch64 (19+12+37+15);
clippy чист. Точность конверсий сохранена: integer BT.601 совпадает с
f32-эталоном в пределах ±1 (тест `integer_helpers_match_f32_reference`).

## 2. Что сделано (по находкам аудита)

### video-capture/convert.rs — integer BT.601 + chunk-итераторы
Проблема: все пиксельные циклы — скалярный f32 (`round().clamp()` ×3 на
пиксель, библиотечный round), bounds-checked индексация, per-pixel адресная
арифметика; `rgb24_to_nv12` гонял хрому u8→f32→round→u8 туда-обратно и
держал ветвление с делением `count` в каждом 2×2-блоке.
Решение: ×256 fixed-point integer-коэффициенты (77/150/29, 359/88/183/454,
43/85/128, 128/107/21), посточные `chunks_exact`-итераторы (bounds-checks
исчезают на уровне компилятора), UV — среднее raw i32-хромы `>>10`,
парная обработка пикселей YUYV ([Y0 U Y1 V] → 6 байт RGB одной копией).
f32-хелперы оставлены как эталон для тестов согласованности.

### yolov8 — память-локальность и LUT
Проблема: `postprocess` сканировал 672K значений классов со страйдом
8400×4Б = 33.6 КБ (cache-miss на каждое чтение); box-строки читались до
порога; `letterbox` делал f32 mul+round и индексную арифметику на каждый
пиксель; `rgb_to_nchw` делил на 255.0.
Решение: транспонированный классовый скан (80 последовательных проходов по
континуальным строкам, лучшие класс/скор — в компактные рабочие массивы,
L1/L2-резидентные); box-строки — только для прошедших порог; letterbox —
LUT исходных столбцов один раз на кадр + построчные срезы + memcpy-fast-path
при scale==1; NCHW — умножение на 1/255 + chunks.

### cv-inference — аллокации и UTF-8
`base64_encode`: `String::push(char)` выполнял UTF-8-энкод на каждый символ
(1.8M на кадр 640×640 RGB) + 2 ветвления длины на каждый 3-байтовый чанк →
`Vec<u8>` c `[u8;4]`-квадами без ветвлений + хвостовой match + одна
валидация `from_utf8` (выход base64 — ASCII).
`cpu_onnx`: кэш имени входа при init (была String-аллокация на кадр);
`nv12_to_rgb24` → integer парная конверсия (тот же паттерн, что convert.rs).

### cv-visualizer
`encode_jpeg(&RgbImage)` делал `img.clone()` (полный кадр) только чтобы
отдать владение `DynamicImage` → функция принимает кадр по значению.

## 3. Найдено, но НЕ оптимизировано (реестр на будущее)

| Кандидат | Оценка | Почему отложено |
|---|---|---|
| **NEON SIMD** (std::arch::aarch64) для конвертеров и NCHW | ещё ×3-8 | unsafe-intrinsics + cfg(target_arch); текущие цифры уже ≥ NPU-инференса по необходимости; отдельная задача |
| **base64 → SHM** (мост rknn-bridge через shmem-buffer/SCM_RIGHTS) | −60 мс round-trip | интеграционная задача (KNOWN_ISSUES #2), меняет протокол моста |
| `postprocess` SIMD argmax по классам | до ×2 | 2.2 мс — уже не доминанта; выигрыш ниже риска |
| Frame-pool в v4l2_direct (замена `to_vec` на кадр) | ~десятки мкс | API-изменение Frame/канала; аллокатор glibc кэширует большие чанки |
| `multi_tracker`: reuse буферов (cost-matrix Vec<Vec>, HashSets, track_ids) | мкс/кадр при n≫1 | трекер ещё не в прод-контуре (Phase 1.2) |
| JSONL: держать fd открытым между кадрами | syscall/кадр | visualizer — debug-путь, не realtime |
| `letterbox`/`NCHW` выходные буферы (1.2/4.9 МБ на кадр) | аллокации | требует API `*_into` с переиспользуемым буфером; ONNX-путь — x86-dev |

## 4. Влияние на конвейер (оценка)

Приложимый выигрыш зависит от пути:
- **PS Eye (YUYV)**: decode 7.03→~0.9 мс (×7.9) — capture+decode укладывается
  в период кадра с запасом ×3 (16.6 мс @60 FPS → было впритык).
- **NPU-конвейер (live-demo)**: CPU-стадии между захватом и инференсом
  сокращены на ~6.4 мс/кадр; round-trip 90 мс доминируется инференсом/базой —
  главный резерв теперь SHM-мост (см. реестр).
- **x86-dev (ONNX)**: letterbox+NCHW+postprocess = 2.9 мс → 0.9 мс на кадр.
